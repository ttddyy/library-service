# JWT Authentication Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace HTTP Basic with self-issued RS256 access tokens plus rotating, HttpOnly-cookie refresh tokens, and make school scoping multi-school and claim-based.

**Architecture:** A new `auth` package issues tokens (`/api/auth/login|refresh|logout`) using the existing `JdbcUserDetailsManager` for credentials and a `refresh_tokens` table for rotation with family-based reuse detection. All other API requests are validated statelessly by Spring Security's OAuth2 Resource Server using the public key. `SchoolAccountAccess` reads the `schools` claim; `ROLE_SUPER_ADMIN` bypasses school checks.

**Tech Stack:** Spring Boot 4.0.8, Spring Security 7 (oauth2-resource-server, oauth2-jose / Nimbus), JdbcTemplate, PostgreSQL, JUnit 5, spring-security-test, Testcontainers.

**Spec:** `docs/superpowers/specs/2026-10-17-jwt-auth-design.md`

## Global Constraints

- Java 21; Spring Java Format is enforced in the `validate` phase — run `./mvnw spring-javaformat:apply` before every commit.
- Match surrounding style: tabs, `this.` field access, `@author` javadoc, Apache license header (year 2026) on new files, `package-info.java` with `@NonNullApi` for the new package.
- Access token: RS256, header `kid`, claims `iss`, `sub`, `iat`, `exp`, `jti`, `roles` (no `ROLE_` prefix), `schools` (omitted for `SUPER_ADMIN`). Default TTL `5m`.
- Refresh token: 32 bytes `SecureRandom`, Base64URL (no padding); stored only as hex SHA-256; **absolute** lifetime `1d` from login — rotation copies the family's `expires_at`.
- Cookie: `refresh_token=<value>; HttpOnly; Secure(configurable); SameSite=Strict; Path=/api/auth; Max-Age=<seconds until expires_at>`; cleared with `Max-Age=0`.
- `refresh` and `logout` require header `X-Requested-With` (any value); missing → `401`.
- Auth error bodies: `{"error":"invalid_credentials"}` (login) and `{"error":"invalid_refresh_token"}` (refresh); never reveal which credential part failed.
- Response JSON field names: `access_token`, `token_type` (`"Bearer"`), `expires_in` (seconds), `user` (`username`, `roles`, `schools`) — login only.
- Role hierarchy: `ROLE_SUPER_ADMIN > ROLE_SCHOOL_ADMIN > ROLE_USER`. Roles remain global.
- Properties prefix `library-service.auth.*` exactly as in the spec (`issuer`, `access-token-ttl`, `refresh-token-ttl`, `cookie-secure`, `jwt.key-id`, `jwt.private-key`, `jwt.public-key`, `cors.allowed-origins`).
- Missing/invalid keys must fail startup. Dev keys live in `dev/jwt/` at the repo root, never under `src/main/resources`.
- Use the existing `Clock` bean (`ApplicationConfiguration`) for all time.
- Test command: `./mvnw test -Dtest=<ClassName>`; full suite: `./mvnw verify`.

## Review Focus

1. **Login with unknown user, wrong password, disabled user, or missing/blank fields** — all return the identical `401 {"error":"invalid_credentials"}`, never `400`/`500` or a distinguishable message. (Task 5)
2. **Garbage, empty, or unknown `refresh_token` cookie value** — `401 invalid_refresh_token` with the cookie cleared, not `500`. (Task 5)
3. **Token signed by another key, `alg=none`, or wrong issuer** — rejected with `401` and `WWW-Authenticate: Bearer error="invalid_token"`. (Tasks 1, 4)
4. **Non-super-admin user with zero schools** — login succeeds with `schools: []`; every school-scoped call returns `403`. (Task 6)
5. **Refresh exactly at `expires_at`** — treated as expired (`expires_at <= now`). (Task 3)
