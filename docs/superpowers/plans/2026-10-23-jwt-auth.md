# JWT Authentication Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the single Basic-auth user with JDBC-backed users, RS256 access tokens, rotating HttpOnly refresh-token cookies, and role-based authorization rules.

**Architecture:** A new `auth` package issues tokens (`/api/auth/login|refresh|logout`) using `JdbcUserDetailsManager` for credentials and a `refresh_tokens` table for rotation with family-based reuse detection and a grace window. All other `/api/**` requests are validated statelessly by Spring Security's OAuth2 Resource Server with the public key; HTTP Basic stays temporarily against the same JDBC users. Authorization rules come from one table in `ApplicationSecurityConfiguration` with a role hierarchy.

**Tech Stack:** Spring Boot 4.0.8, Spring Security 7 (`spring-boot-starter-oauth2-resource-server`, Nimbus), JdbcTemplate, PostgreSQL, JUnit 5, spring-security-test, Testcontainers.

**Spec:** `docs/superpowers/specs/2026-10-17-jwt-auth-design.md`

## Global Constraints

- Java 21; Spring Java Format is enforced in the `validate` phase — run `./mvnw spring-javaformat:apply` before every commit.
- Match surrounding style: tabs, `this.` field access, `@author Tadaya Tsuyukubo` javadoc on main classes, Apache license header (year 2026) on new files, `package-info.java` with `@NonNullApi` (`org.springframework.lang`) for the new `auth` package, `org.springframework.lang.Nullable`.
- Access token: RS256, header `kid`, claims `iss`, `sub`, `iat`, `exp`, `jti`, `roles` (no `ROLE_` prefix), `schools` (ordered; omitted for `SUPER_ADMIN`).
- Defaults: `issuer=library-service`, `access-token-ttl=15m`, `refresh-token-ttl=1d`, `refresh-reuse-grace=10s`, `cookie-secure=true`; prefix `library-service.auth`.
- Refresh token: 32 bytes `SecureRandom`, Base64URL no padding; stored only as lowercase hex SHA-256; absolute lifetime — successors copy `expires_at`; `expires_at <= now` is expired.
- Cookie: `refresh_token=<value>; HttpOnly; Secure(cookie-secure); SameSite=Strict; Path=/api/auth; Max-Age=<seconds until expires_at>`; cleared with empty value and `Max-Age=0`.
- `refresh` and `logout` require header `X-Requested-With` (any value); missing → `401`.
- Error bodies: `{"error":"invalid_credentials"}` (login), `{"error":"invalid_refresh_token"}` (refresh).
- Response JSON names: `access_token`, `token_type` (`"Bearer"`), `expires_in` (seconds), `user` (`username`, `roles`, `schools`) — login only.
- Role hierarchy: `ROLE_SUPER_ADMIN > ROLE_SCHOOL_ADMIN > ROLE_USER`. Authorities stored with `ROLE_` prefix; passwords with `{bcrypt}`.
- Missing/invalid/mismatched keys fail startup. Dev keys live in `dev/jwt/` at the repo root, never under `src/main/resources`.
- Use the existing `Clock` bean (`ApplicationConfiguration`); tests use `MockClocks.MockClock`.
- Full-context tests need keys: annotate them `@ActiveProfiles("dev")`.
- Test command: `./mvnw test -Dtest=<ClassName>`; full suite: `./mvnw verify`.

## Review Focus

1. **Malformed JSON or empty login body** — `401 invalid_credentials`, not the `400` Spring would produce. (Task 5: `malformedBodyIsInvalidCredentials`)
2. **Two refreshes of the same token racing** — the second inside the grace window gets `200` without `Set-Cookie`; the family survives. (Task 3: `reuseWithinGraceReturnsUsernameWithoutSuccessor`, Task 6 flow)
3. **Reuse detected while throwing** — the family deletion must commit even though `InvalidRefreshTokenException` is thrown inside the transaction. (Task 3: `reuseOutsideGraceDeletesFamily` asserts rows are gone after the call)
4. **Wrong Basic password from the UI** — `401` with a Bearer challenge only; no `WWW-Authenticate: Basic` (browser popup). (Task 4: `badBasicCredentialsSendNoBasicChallenge`)
5. **User disabled after login** — next refresh returns `401` and the family is gone. (Task 5: `refreshForDisabledUserRevokesFamily`)
